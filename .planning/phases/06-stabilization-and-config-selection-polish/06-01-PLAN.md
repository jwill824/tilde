# Phase 06 Plan 01: Stabilization and Config Selection Polish

## Objective

Close the three Phase 6 stabilization issues with tests-first changes:

1. Generated JavaScript/package output must not incorrectly copy or expose `.tsx` source content.
2. `tilde plugin list` must report plugin ownership/source in a way that is explicit and explainable.
3. Interactive flows must prompt or clearly explain when tilde is about to use an auto-discovered config because no explicit config source was provided.

## Success Criteria

- `npm run build` output passes a deterministic artifact check for #52.
- `tilde plugin list` output is covered by tests and no longer leaves users guessing where `first-party` came from.
- Discovered config use is confirmed or clearly explained in interactive startup/config-first behavior.
- Explicit config sources (`--config`, `TILDE_CONFIG`, positional paths) continue to bypass discovered-config prompting.
- Targeted unit/integration tests pass.

## Wave 0: Reproduce and Pin Regressions

### Task 06-01-01: Add failing artifact and plugin-list regression tests

**Goal:** Prove the current behavior for #52 and #60 before fixing it.

**Implementation notes:**

- Add a targeted test or script-backed test that builds or inspects built artifacts for generated `.js` files incorrectly copying `.tsx` content/references.
- Add CLI regression coverage for `tilde plugin list`.
- Keep assertions stable and user-facing: avoid overfitting to whitespace beyond column/order expectations already present in the command.

**Likely files:**

- `tests/integration/cli-regression.test.ts`
- `tests/unit/read-package-version.test.ts` or a new focused unit test if artifact inspection does not need the built CLI
- `src/index.tsx`

**Verification:**

- `npm run build`
- `npm run test:integration -- tests/integration/cli-regression.test.ts`

### Task 06-01-02: Add discovered-config prompt/explanation regression tests

**Goal:** Pin the desired #74 behavior before changing startup logic.

**Implementation notes:**

- Cover discovered config source separately from explicit `--config` and `TILDE_CONFIG`.
- Prefer built CLI regression tests where possible because startup routing lives in `src/index.tsx`.
- For Ink-specific confirmation UI, use existing `ink-testing-library` patterns in `tests/integration/wizard-flow.test.tsx` or `tests/integration/config-first.test.ts`.
- Do not add prompts to non-interactive config-required commands.

**Likely files:**

- `tests/integration/cli-regression.test.ts`
- `tests/integration/config-first.test.ts`
- `tests/integration/wizard-flow.test.tsx`
- `src/app.tsx`
- `src/modes/config-first.tsx`

**Verification:**

- `npm run test -- tests/unit/config-discovery.test.ts`
- `npm run build && npm run test:integration -- tests/integration/cli-regression.test.ts`

## Wave 1: Implement Stabilization Fixes

### Task 06-01-03: Fix generated JS/source artifact behavior

**Goal:** Ensure build/package outputs represent compiled runtime artifacts cleanly and do not copy `.tsx` source content into generated `.js` artifacts incorrectly.

**Implementation notes:**

- Start from the failing check in Task 06-01-01.
- Keep `tsconfig.json`, `tsconfig.bin.json`, and package `files` behavior aligned.
- Preserve the npm binary entry at `dist/bin/tilde.js`.
- Do not add broad build tooling unless TypeScript configuration cannot express the fix.

**Verification:**

- `npm run build`
- The new artifact regression test

### Task 06-01-04: Make plugin ownership/source explainable

**Goal:** Replace ambiguous plugin list source output with explicit ownership/source semantics that map cleanly to registry metadata.

**Implementation notes:**

- Consider adding a formatter/helper for plugin-list rows rather than embedding formatting in `handlePluginSubcommand()`.
- Keep existing `TildePlugin.source` contract compatible unless a narrow type/schema change is clearly justified.
- If introducing display labels, keep machine-readable source values available in code and tests.
- Avoid widening the central `PluginRegistry` to browser/editor/AI metadata unless required for this issue; Phase 8/9 owns broader registry/search work.

**Verification:**

- `npm run test -- tests/unit/tool-metadata.test.ts`
- `npm run build && npm run test:integration -- tests/integration/cli-regression.test.ts`

### Task 06-01-05: Prompt or explain discovered config use in interactive startup

**Goal:** When a config exists but was not specified via `--config`, interactive flows should ask the user to use it or continue fresh, or otherwise clearly explain the selection before proceeding.

**Implementation notes:**

- Reuse the existing `ConfigPathSource` from `src/utils/config-resolution.ts`.
- Thread source information into `App` or config-first mode only as far as needed for UI behavior.
- Preserve explicit-source precedence and existing no-config guidance.
- Non-interactive config-required commands should stay deterministic and not prompt.

**Verification:**

- `npm run test -- tests/unit/config-discovery.test.ts`
- Relevant Ink integration test(s)
- `npm run build && npm run test:integration -- tests/integration/cli-regression.test.ts`

## Risks

- #52 is underspecified; the first task must reproduce the actual faulty artifact before implementation.
- Adding prompts in the wrong layer could break non-interactive config-first use. Keep prompt behavior tied to interactive startup only.
- Plugin ownership labels overlap with future registry/search UX. Keep Phase 6 to explanation and correctness, not broad registry redesign.
